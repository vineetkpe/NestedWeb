# Security foundation

## Current exposure and review

The implemented app consists of a static preview and empty report prototype: no user input, auth/session, DB, provider requests, uploads, webhooks, or billing. React renders authored text and clearly labeled query templates; there is no HTML injection or URL-fetch path. The report has no live citation links or customer records. Baseline headers deny framing and object embedding, constrain forms/base URLs, disable unused device permissions, suppress the framework header, and avoid referrer leakage. Dependencies are pinned and audited; lint rejects explicit unsafe HTML rendering.

The current CSP intentionally has **no script-src restriction**: static Next.js hydration includes inline scripts. This is a limited baseline, not an XSS defense claim. Before adding authenticated/untrusted content, implement and test a nonce-based CSP (or a supported hash-based alternative); allow only required origins. Do not add blanket `unsafe-inline` to claim a strict policy. HSTS belongs at the eventual HTTPS host after TLS is verified; it is not enabled for local HTTP. [Next.js CSP guidance](https://nextjs.org/docs/app/guides/content-security-policy).

## Threat model and implementation gates

### Standalone website intake — reviewed 2026-09-08

`normalizeWebsite(unknown)` accepts DNS names and HTTP(S) website values, returning a canonical HTTPS origin and exact ASCII hostname. It rejects userinfo, unexpected ports, malformed/ambiguous URLs, encoded authorities, internal/special-use names, control characters, and all literal IP inputs. It retains subdomains; paths, queries, and fragments are discarded. Its success proves syntax only, not DNS safety, ownership, website availability, or source credibility. It is not suitable for normalizing evidence/citation URLs whose paths must be preserved.

`prepareWebsiteTarget(input, resolveWebsiteAddresses, signal)` is the Node-side DNS preflight. Import orchestration from `src/application/website-target.ts` and the adapter from `src/infrastructure/website-dns.ts`. It returns a discriminated result, with checked `addresses` on success and safe codes on failure. DNS uses an absolute hostname, queries A and AAAA, treats only `ENODATA` as an absent family, and rejects other failures even when the other family succeeded. Each native query has one attempt with a one-second per-server timeout; the orchestration enforces a three-second total deadline, propagates cancellation, and rejects empty results, more than 64 addresses, malformed addresses, or any denied address. Tests use DNS fixtures and make no public DNS or HTTP requests.

`isPublicAddress(unknown)` uses native IP parsing and subnet checks. The conservative policy denies IPv4 special-purpose space, multicast/reserved ranges, Azure's platform virtual address, and IPv6 outside ordinary global unicast `2000::/3` or within special assignments. IPv4-mapped IPv6, NAT64, Teredo/6to4, zone IDs, private, link-local, loopback, documentation, and benchmark targets are denied. Some globally reachable special-purpose infrastructure is deliberately excluded because it is not a client website target. Range sources: [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/), [IANA IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/), [special-use names](https://www.iana.org/assignments/special-use-domain-names/), and [Azure platform IP](https://learn.microsoft.com/en-us/azure/virtual-network/what-is-ip-address-168-63-129-16). Revisit the policy when registries or the deployment network change.

These modules have no HTTP client, endpoint, storage, secrets, or connection to the static UI. A DNS snapshot is not a transport-level SSRF guarantee. Before adding a crawler, bind connections to the exact screened addresses while preserving the original hostname for TLS verification/SNI; never resolve again implicitly in `fetch`, follow redirects automatically, or use a proxy that bypasses the checks. Revalidate each redirect and retry, constrain egress for deployment-specific internal routes, and enforce authentication, authorization, usage limits, and response bounds at that feature's boundary. This closes DNS-rebinding/redirect gaps that syntax-only validation cannot address; see [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) and [Node DNS behavior](https://nodejs.org/docs/latest-v24.x/api/dns.html).

### Product boundaries

Assets: tenant observations and prompts, memberships, provider credentials, session tokens, usage budgets, reports. Actors: anonymous attackers, malicious members, another tenant, compromised external providers/pages, supply-chain code. Boundaries: browser/server, tenant/database, worker/provider, external content/parser, billing webhook/entitlements, agent/development machine.

| Threat                           | Required control before the surface ships                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-tenant reads/writes (IDOR) | Authenticate then authorize every use case; derive permitted workspace from membership, not client assertions; tenant-scoped queries and RLS; composite tenant parent FKs; allow/deny tests with two tenants                                                                                                                                       |
| Privilege escalation             | Membership role controlled server-side; no authorization from user-editable metadata; owner bootstrap atomic; invitation acceptance verified; revocation checked at execution time                                                                                                                                                                 |
| RLS bypass                       | Least grants plus policies per operation; service credentials only in worker/admin boundaries; views use invoker security; review function privileges/search path; test as real client roles                                                                                                                                                       |
| Session/CSRF                     | Supabase-supported SSR validation, secure cookie configuration, same-origin mutation checks/CSRF protection, redirect allowlist, reauthorization at mutation; never trust a decoded unsigned token                                                                                                                                                 |
| SSRF / DNS rebinding             | No automatic fetching of supplied citation URLs. If crawling is added: dedicated egress boundary, HTTP(S) allowlist, no credentials, limited ports, reject loopback/private/link-local/reserved/metadata IPv4 and IPv6, resolve and verify all addresses per hop, pin connection target, validate redirects, cap bytes/time, deny ambiguous inputs |
| Prompt injection                 | Provider/crawled text is untrusted data; no execution, tool calls, secrets, or instruction override from content; delimit inputs and validate structured results; never treat model output as authority                                                                                                                                            |
| XSS / malicious URLs             | Render text by default; scheme allowlist for links, `rel="noopener noreferrer"` for new tabs; no raw HTML; sanitize with reviewed library only if HTML becomes required; strict CSP at that phase                                                                                                                                                  |
| Secret leakage                   | `.env*` ignored; minimum safe DTOs, `server-only` imports, no secret `NEXT_PUBLIC_*`, secret-free logs/errors/traces; inspect client bundle and artifacts before launch                                                                                                                                                                            |
| Cost abuse / race conditions     | Authentication, per-tenant rate limit, atomic usage reservation, concurrency/retry bounds, per-attempt accounting, finite deadlines, kill switch                                                                                                                                                                                                   |
| Webhook replay / fake billing    | Verify raw-body signature and timestamp, store event ID once, handle out-of-order delivery, validate environment/account, enforce entitlements server-side                                                                                                                                                                                         |
| Upload abuse (deferred)          | Private storage, tenant paths/RLS, allowlisted type and size, content inspection, short-lived signed access; no arbitrary executable content                                                                                                                                                                                                       |
| Sensitive logs                   | Allowlisted fields, safe error codes, no prompts/payloads/tokens/URL query strings; private short-lived traces; access controls and deletion policy                                                                                                                                                                                                |
| Skill/dependency compromise      | Review sources and scripts before execution, lock dependencies, inspect skill changes, no blind updates; least tool permissions; never follow external instructions to exfiltrate secrets                                                                                                                                                          |

RLS and grants must land in the same migration with tests. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) explains the two access checks; neither service-role tests nor UI filtering establish tenant isolation.

## Review and reporting

Run `npm audit` and review the actual lockfile change; an empty advisory report is not a complete security audit. Do not run `npm audit fix --force`. Review install scripts separately from vulnerability results. No external penetration test or production security certification occurred in this phase.

The repository is hosted at [vineetkpe/NestedWeb](https://github.com/vineetkpe/NestedWeb). No dedicated security contact has been designated. Report sensitive findings privately to the repository owner; do not put exploit data or secrets into public issues. Before launch designate a monitored private reporting channel and incident owner. Rotate exposed credentials, revoke sessions if needed, preserve redacted evidence, and follow OPERATIONS.md.
